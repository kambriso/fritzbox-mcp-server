== Einleitung

=== Was ist das?

Dieser MCP-Server ermöglicht die Interaktion mit deiner FRITZ!Box über KI-Assistenten.
Stelle Fragen in natürlicher Sprache, analysiere dein Netzwerk, verwalte Geräte, behebe Probleme und konfiguriere Einstellungen - ohne die Web-Oberfläche zu berühren.

=== So funktioniert es (Sicherheitsarchitektur)

image::architecture.svg[Architektur-Diagramm]

Der MCP-Server läuft auf deinem Computer und fungiert als sichere Brücke zwischen KI-Agenten (die in der Cloud laufen) und deiner FRITZ!Box (die komplett lokal bleibt).

Deine FRITZ!Box-Zugangsdaten werden lokal in einer `.env` Datei auf deinem Computer gespeichert.
Der MCP-Server verwendet diese Zugangsdaten nur für die Kommunikation mit deiner FRITZ!Box über dein lokales Netzwerk.

Der KI-Agent erhält nur die Ergebnisse (wie "3 Geräte verbunden" oder "Router-Laufzeit: 5 Tage"), niemals deine Zugangsdaten oder direkten Zugriff auf deinen Router.

Kritische Sicherheitsmerkmale:

* Deine FRITZ!Box braucht keine Internet-Exposition
* Keine Ports müssen geöffnet werden
* Keine Cloud-Verbindung zu deinem Router
* Zugangsdaten bleiben auf deinem Computer
* Alle Router-Kommunikation erfolgt nur über dein lokales Netzwerk

=== Warum diesen Server nutzen?

Funktioniert mit ALLEN FRITZ!Box-Modellen und Firmware-Versionen.
Wenn AVM neue Features oder Modelle veröffentlicht, passt sich dieser Server automatisch an.
Keine Updates nötig.

Anders als andere Lösungen, die bei Firmware-Updates kaputt gehen oder nur mit bestimmten Modellen funktionieren, erkennt dieser Server die Fähigkeiten deines Routers in Echtzeit.

=== Schnellstart

==== 1. Installation

===== Automatische Installation (Linux/macOS - Empfohlen)

Download und Installation mit automatischer Checksummen-Verifizierung:

[source,bash]
----
curl -fsSL https://raw.githubusercontent.com/kambriso/fritzbox-mcp-server/main/install.sh | sh
----

Der Installer wird:

* Deine Plattform (OS und Architektur) automatisch erkennen
* Die neueste Version von GitHub herunterladen
* SHA256-Checksummen zur Sicherheit verifizieren
* Nach `~/.local/bin/fritz-mcp` installieren
* Die Binärdatei ausführbar machen

[TIP]
====
Installation anpassen:

[source,bash]
----
# Spezifische Version installieren
FRITZBOX_MCP_VERSION=<tag> curl -fsSL https://raw.githubusercontent.com/kambriso/fritzbox-mcp-server/main/install.sh | sh

# In benutzerdefiniertes Verzeichnis installieren
FRITZBOX_MCP_INSTALL_DIR=/usr/local/bin curl -fsSL https://raw.githubusercontent.com/kambriso/fritzbox-mcp-server/main/install.sh | sh
----
====

===== Manuelle Installation (Alle Plattformen)

Lade die Binärdatei für dein System von https://github.com/kambriso/fritzbox-mcp-server/releases[Releases]:

Linux:: `fritz-mcp-linux-amd64.tar.xz` oder `fritz-mcp-linux-arm64.tar.xz`
macOS:: `fritz-mcp-darwin-amd64.tar.xz` oder `fritz-mcp-darwin-arm64.tar.xz`
Windows:: `fritz-mcp-windows-amd64.zip` oder `fritz-mcp-windows-arm64.zip`

Entpacke das Archiv und mache es ausführbar (Linux/macOS):
[source,bash]
----
tar -xJf fritz-mcp-linux-amd64.tar.xz
chmod +x fritz-mcp
----

Windows: Entpacke die ZIP-Datei.

==== 2. Konfigurationsdatei erstellen

Erstelle eine Datei namens `.env` mit deinen FRITZ!Box-Zugangsdaten:

[source,bash]
----
FRITZ_HOST=fritz.box
FRITZ_USERNAME=dein-benutzername
FRITZ_PASSWORD=dein-passwort
----

Speichere diese Datei an einem dieser Orte:

Windows:: `%USERPROFILE%\.config\fritzbox-mcp-server\.env`
macOS:: `~/.config/fritzbox-mcp-server/.env`
Linux:: `~/.config/fritzbox-mcp-server/.env`

Oder lege sie zum Testen im gleichen Ordner wie die Binärdatei ab.

[WARNING]
====
Diese Datei enthält dein Passwort.
Halte sie sicher und committe sie niemals in die Versionsverwaltung.

Unter Linux/macOS: Zugriff beschränken mit `chmod 600 ~/.config/fritzbox-mcp-server/.env`
====

==== 3. FRITZ!Box Benutzerberechtigungen

Dein FRITZ!Box-Benutzer benötigt vollen Zugriff auf die Einstellungen.

In der FRITZ!Box Web-Oberfläche (http://fritz.box):

1. Gehe zu System → FRITZ!Box-Benutzer → [Dein Benutzer] → Berechtigungen
2. Aktiviere: "FRITZ!Box-Einstellungen" (oder "Der Benutzer kann alle Einstellungen der FRITZ!Box sehen und bearbeiten")

==== 4. Claude Desktop konfigurieren

Bearbeite deine Claude Desktop Konfigurationsdatei:

Windows:: `%APPDATA%\Claude\claude_desktop_config.json`
macOS:: `~/Library/Application Support/Claude/claude_desktop_config.json`
Linux:: `~/.config/claude/claude_desktop_config.json`

Füge den Server hinzu:

[source,json]
----
{
  "mcpServers": {
    "fritzbox": {
      "command": "/pfad/zur/fritz-mcp"
    }
  }
}
----

[TIP]
====
Windows: `C:\\Users\\DeinName\\pfad\\zur\\fritz-mcp.exe` (beachte die doppelten Backslashes)

macOS/Linux mit automatischer Installation: `~/.local/bin/fritz-mcp`

macOS/Linux mit manueller Installation: Absoluter Pfad zur Binärdatei, z.B. `/Users/deinname/bin/fritz-mcp`
====

Starte Claude Desktop neu.

==== Supply-Chain-Sicherheit (Supply chain Levels for Software Artifacts, SLSA)

Dieses Projekt stellt https://slsa.dev[SLSA]-Provenienz (Supply chain Levels for Software Artifacts) für alle Release-Binärdateien bereit.
SLSA-Provenienz attestiert kryptographisch, dass Binärdateien aus spezifischem Quellcode von einem vertrauenswürdigen Builder erstellt wurden.

Zwei unabhängige Nachweise sind verfügbar:

1. SHA256SUMS - Forge-übergreifende Reproduzierbarkeit (gleicher Quellcode erzeugt identische Binärdateien auf GitLab und GitHub)
2. SLSA-Provenienz - Supply-Chain-Attestierung (beweist Binär-Herkunft und Build-Prozess)

===== GitLab (SLSA Level 2)

GitLab-Releases enthalten SLSA Level 2 Provenienz via `artifacts-metadata.json`.

Verifizierung:

[source,bash]
----
# Binary und SLSA-Metadaten herunterladen
glab release download <tag> -R kambriso/fritzbox-mcp-server \
  -n 'fritz-mcp-linux-amd64' -n 'artifacts-metadata.json' # <1>

# Provenienz prüfen
cat artifacts-metadata.json | jq '.predicateType'
# Ausgabe: "https://slsa.dev/provenance/v1"

# Artefakt-Digest verifizieren
sha256sum fritz-mcp-linux-amd64
# Mit Digest in artifacts-metadata.json subjects vergleichen
----
<1> Der Git-Tag zum Verifizieren, z.B. `v0.7.7`

Die Provenienz enthält:

* In-toto Statement-Format (`https://in-toto.io/Statement/v0.1`)
* SLSA v1 Prädikat mit Build-Definition
* SHA256-Digests für alle Artefakte
* GitLab CI Umgebungsparameter

===== GitHub (SLSA Level 3)

GitHub-Releases enthalten SLSA Level 3 Provenienz via https://github.com/slsa-framework/slsa-github-generator[slsa-github-generator].

Verifizierung mit slsa-verifier:

[source,bash]
----
# Binärdatei und Provenienz herunterladen
gh release download <tag> -R kambriso/fritzbox-mcp-server \
  -p 'fritz-mcp-linux-amd64' -p '*.intoto.jsonl'

# Provenienz verifizieren

  verify-artifact fritz-mcp-linux-amd64 \
  --provenance-path multiple.intoto.jsonl \
  --source-uri github.com/kambriso/fritzbox-mcp-server \
  --source-tag <tag> # <1>
----
<1> Der zu verifizierende Git-Tag, z.B. `v0.7.7`

===== Cosign-Signatur-Verifizierung

Alle Binärdateien sind mit https://docs.sigstore.dev/cosign/[Cosign] und schlüsselloser Signierung (OIDC) signiert.
Signaturen und Zertifikate sind in den Release-Artefakten enthalten.

[source,bash]
----
# Binärdatei, Signatur und Zertifikat herunterladen
# (von GitLab-Artefakten oder GitHub-Release)

# Signatur verifizieren
cosign verify-blob \
  --signature fritz-mcp-linux-amd64.sig \
  --certificate fritz-mcp-linux-amd64.pem \
  --certificate-oidc-issuer https://gitlab.com \
  fritz-mcp-linux-amd64
----

===== Unabhängige Verifizierung

Alle Verifizierungen können offline mit Standard-Tools durchgeführt werden:

[source,bash]
----
# 1. Prüfsummen zwischen Forges vergleichen
diff <(curl -sL gitlab-SHA256SUMS) <(curl -sL github-SHA256SUMS)

# 2. Binärdatei gegen Prüfsumme verifizieren
sha256sum -c SHA256SUMS

# 3. SLSA-Provenienz verifizieren (slsa-verifier oder manuelle Prüfung)
# 4. Cosign-Signatur verifizieren (benötigt Netzwerk für Zertifikatskette)

# Vollständige Vertrauenskette: Quellcode -> CI-Build -> signiertes Artefakt -> dein Rechner
----

==== Cross-Git-Forge Verifizierung

Dieses Projekt veröffentlicht identische Releases auf GitLab und GitHub.
Cross-Forge-Verifizierung beweist, dass keine der Forges kompromittiert wurde - wenn ein Angreifer Binärdateien auf einer Forge modifiziert hätte, würden die Prüfsummen nicht übereinstimmen.

Dies ist unabhängig von SLSA: Während SLSA beweist "diese Binärdatei stammt aus diesem Quellcode", beweist Cross-Forge-Verifizierung "beide Forges liefern dieselbe Binärdatei".

[source,bash]
----
# Prüfsummen von beiden Forges herunterladen
curl -sL "https://gitlab.com/.../SHA256SUMS" -o gitlab-SHA256SUMS
curl -sL "https://github.com/.../SHA256SUMS" -o github-SHA256SUMS

# Vergleichen - muss identisch sein
diff gitlab-SHA256SUMS github-SHA256SUMS && echo "Cross-Forge Verifizierung bestanden"

# Oder mit CLI-Tools:
gh release download <tag> -R kambriso/fritzbox-mcp-server -p 'SHA256SUMS' -D github
glab release download <tag> -R kambriso/fritzbox-mcp-server -n 'SHA256SUMS' -D gitlab
diff github/SHA256SUMS gitlab/SHA256SUMS
----

Warum das wichtig ist:

* Schützt vor Kompromittierung einer einzelnen Forge
* Validiert, dass reproduzierbare Builds korrekt funktionieren
* Kein Vertrauen in eine einzelne Plattform erforderlich
* Benutzer können mit Standard-Tools verifizieren (curl, diff, sha256sum)

=== Token-Nutzung Hinweise

Dieser MCP-Server stellt 143 Tools für den KI-Assistenten bereit.
Jede Tool-Definition (Name, Beschreibung, JSON-Schema) wird mit jeder Nachricht gesendet.

==== Auswirkungen auf Claude Code / Claude API

* Token-Overhead: ~25.000-30.000 Tokens pro Nachricht nur für Tool-Definitionen
* Kostenabschätzung: ~$0,08/Nachricht (Sonnet) oder ~$0,45/Nachricht (Opus) an Tool-Overhead
* Kontext-Nutzung: Tool-Schemas verbrauchen Kontext-Fenster-Platz, der für Konversation genutzt werden könnte

==== Empfehlungen

===== Für gelegentliche Nutzung
Deaktiviere den Server wenn nicht benötigt:

[source,bash]
----
# In Claude Code, MCP-Server deaktivieren:
claude --mcp-server fritzbox=off

# Oder aus mcpServers in ~/.claude.json entfernen
----

===== Für häufige Nutzung
Erwäge die Aktivierung nur für spezifische Projekte die Router-Zugriff benötigen, anstatt global.

===== Für lokale LLMs
Bei Verwendung mit lokalen Modellen (llama.cpp, Ollama) können 143 Tools kleinere Modelle überfordern.
Verwende Tool-Filterung um nur benötigte Tools bereitzustellen.

[TIP]
====
Nach der ersten Nachricht in einer Session reduziert Claudes Prompt-Caching die Token-Kosten für folgende Nachrichten.
Der Overhead ist am bedeutendsten bei kurzen Konversationen.
====

== Entwicklerhandbuch

=== Architektur

Dieser Server ist laufzeitgesteuert und modellunabhängig:

* Keine hartkodierten Service-Strukturen
* Erkennt Fähigkeiten dynamisch aus den Service-Deskriptoren deiner FRITZ!Box
* Funktioniert automatisch mit Firmware-Updates
* Unterstützt alle FRITZ!Box-Modelle (getestet mit 7490, 7590)

=== MCP SDK Auswahl

Dieses Projekt verwendet das Community MCP SDK (https://github.com/mark3labs/mcp-go[mark3labs/mcp-go] v0.7.0) anstelle des offiziellen SDK (modelcontextprotocol/go-sdk) aufgrund von Kompatibilitätsproblemen:

* Offizielle SDK Probleme: Tools erscheinen nicht in MCP-Clients trotz korrekter Registrierung
** https://github.com/modelcontextprotocol/go-sdk/issues/395[Issue #395]: Initialisierungs-Race-Conditions und Client-Timeouts
** https://github.com/modelcontextprotocol/go-sdk/issues/200[Issue #200]: Schema-Generierungsprobleme mit Pointer-Typen (behoben in PR #338)
* Community SDK: Praxiserprobt, keine bekannten Kompatibilitätsprobleme
* API-Inkompatibilität: Die beiden SDKs sind nicht API-kompatibel (siehe https://github.com/modelcontextprotocol/go-sdk/blob/main/design/design.md[offizielles SDK Design-Dokument])

Das offizielle SDK verwendet eine andere JSON-RPC-Implementierung und eine niedrigere Transport-Schnittstelle.
Während beide SDKs eigenständig funktionieren, hat sich das Community SDK als zuverlässiger für stdio-Transport mit Claude Code Clients erwiesen.

==== WASI Build Hinweise

Ein WASI (WebAssembly System Interface) Build ist enthalten um Code-Portabilität zu demonstrieren.
Go's wasip1-Target hat jedoch erhebliche Einschränkungen für Netzwerkanwendungen:

* Kein Netzwerkzugriff - Go unterstützt nur WASI Preview 1, dem Socket-APIs fehlen
* Eingeschränkter Dateisystemzugriff
* Bietet Capability-basierte Sicherheits-Sandbox

NOTE: Während WasmEdge Sockets unterstützt und WASI Preview 2 wasi-sockets enthält, zielt Go derzeit nur auf wasip1 (versiegelt ohne Netzwerk).
WASI Preview 2 wurde im Januar 2024 gestartet, aber Go hat keinen angekündigten Zeitplan für GOOS=wasip2 Unterstützung (verfolgt in https://github.com/golang/go/issues/65333[Issue #65333]).
Go 1.24 (Feb 2025) und Go 1.25 (Aug 2025) enthalten kein wasip2.

Empfehlung: Verwende native Binärdateien oder Multi-Arch-Container für Produktion.
Der WASI-Build demonstriert WebAssembly-Portabilität, kann aber mit aktuellen Go-Releases nicht als Netzwerkdienst funktionieren.

Bauen für spezifische Plattform:

[source,bash]
----
GOOS=linux GOARCH=amd64 make dist
GOOS=darwin GOARCH=arm64 make dist
GOOS=windows GOARCH=amd64 make dist
----

==== Reproduzierbare Builds

Alle Release-Binärdateien sind reproduzierbar: Das Bauen aus dem gleichen Quellcode erzeugt byte-für-byte identische Binärdateien.
Dies ermöglicht unabhängige Verifizierung, dass veröffentlichte Binärdateien mit dem Quellcode übereinstimmen.

===== Warum Reproduzierbarkeit wichtig ist

Reproduzierbare Builds ermöglichen:

* Unabhängige Verifizierung von Release-Artefakten
* Erkennung von Supply-Chain-Manipulation
* Vertrauen, dass Binärdateien mit geprüftem Quellcode übereinstimmen
* Grundlage für SLSA-Attestierungen

===== Build-Flags für Reproduzierbarkeit

Das Makefile verwendet diese Flags um deterministische Builds sicherzustellen:

[source,bash]
----
-trimpath                    # Entfernt absolute Pfade
-buildvcs=false              # Deaktiviert VCS-Info-Einbettung
-buildid=                    # Löscht Build-ID
SOURCE_DATE_EPOCH=$(git)     # Verwendet Commit-Zeitstempel
----

===== Toolchain-Anforderungen

Go erzeugt reproduzierbare Binärdateien bei Verwendung der gleichen Toolchain-Distribution.
Verschiedene Go-Distributionen (Upstream vs Fedora/Debian-Pakete) können jedoch unterschiedliche Binärdateien erzeugen aufgrund distributions-spezifischer Patches oder Build-Experimente.

Bekannte Unterschiede:

* Fedora Go 1.25.6 enthält `GOEXPERIMENT=nodwarf5` in die Toolchain kompiliert
* Upstream Go 1.25.6 (von go.dev oder golang:1.25 Container) hat keine Experimente
* Diese Unterschiede sind in der `.go.buildinfo` Sektion eingebettet

===== Lokale Builds verifizieren

Um GitLab CI Builds lokal zu reproduzieren, verwende den gleichen golang:1.25 Container:

[source,bash]
----
# Alle Plattformen im Container bauen (entspricht CI-Umgebung)
make dists-container

# Mit veröffentlichten Release-Checksummen vergleichen
sha256sum -c SHA256SUMS
----

Das golang:1.25 Docker-Image entspricht der Upstream Go Distribution und gewährleistet Reproduzierbarkeit über Umgebungen hinweg.

===== CI/CD Reproduzierbarkeit

Sowohl GitLab CI als auch GitHub Actions verwenden die offizielle Go 1.25 Toolchain: GitLab über das golang:1.25 Container-Image, GitHub über actions/setup-go das von go.dev herunterlädt.
Beide erzeugen byte-für-byte identische Binärdateien.
Lokale Builds mit distributions-bereitgestellten Go-Paketen (Fedora, Ubuntu, etc.) können unterschiedliche Binärdateien erzeugen aufgrund distro-spezifischer Patches.

Für byte-für-byte reproduzierbare lokale Builds verwende `make dists-container` das im golang:1.25 Container baut.

=== Release-Prozess

Releases werden automatisch im öffentlichen Repository veröffentlicht wenn ein Versions-Tag gepusht wird.

==== Setup

Das `PUBLIC_REPO_TOKEN` Secret ist konfiguriert und bereit für Releases.

==== Ein Release erstellen

[source,bash]
----
# Sicherstellen dass alle Tests bestehen
make check

# Das Release taggen (verwende semantische Versionierung)
git tag v1.0.0

# Den Tag pushen um den Release-Workflow auszulösen
git push origin v1.0.0
----

Die GitHub Actions Workflows werden:

Release Workflow (link:.github/workflows/release.yml[release.yml])::
. Binärdateien für alle Plattformen bauen (Linux, macOS, Windows, WASI)
. SHA256 Checksummen generieren
. Ein Release in https://github.com/kambriso/fritzbox-mcp-server erstellen
. Alle Binärdateien und Checksummen hochladen

Container Workflow (link:.github/workflows/container.yml[container.yml])::
. WASI Container-Image bauen (getaggt mit `-wasi` Suffix)
. Multi-Arch Container bauen (linux/amd64, linux/arm64)
. Zu ghcr.io/kambriso/fritzbox-mcp-server veröffentlichen

NOTE: Verwende den Multi-Arch Container für Produktion.
Der WASI Container demonstriert Portabilität aber Go's wasip1-Target hat keine Netzwerk-Unterstützung (bis wasip2 Unterstützung in zukünftigen Go-Versionen).

==== Unterstützte Release-Plattformen

Binärdateien::
* Linux: amd64, arm64, 386, arm
* macOS: amd64 (Intel), arm64 (Apple Silicon)
* Windows: amd64, arm64
* WASI: wasm (Go wasip1 - keine Netzwerk-Unterstützung bis wasip2)

Container Images::
* Multi-arch: linux/amd64, linux/arm64 (empfohlen für Produktion)
* WASI: wasm (Portabilitäts-Demo - Go wasip1 fehlen Netzwerk-APIs)
